Dictamen de Arquitectura & Seguridad

Portal Pacientes vs. Acceso Administrativo

Análisis técnico exhaustivo para la plataforma médica Holística: ¿Conviene tener todo en una sola aplicación o separar en dos aplicaciones independientes?

RECOMENDACIÓN FINAL DEL INGENIERO

Opción 1: Un Solo Proyecto Modular (Next.js + Supabase RLS)

Es la opción más segura, rápida de desarrollar, económica y fácil de mantener. La seguridad no se logra separando proyectos, sino configurando las políticas Row Level Security (RLS) en Supabase y el Middleware de Next.js.

Opción 1: Todo en Una App

Monolito Modular con Roles (Next.js 16)

Una sola aplicación en Next.js donde la pantalla principal (Imagen 1) actúa como bifurcador. El paciente inicia sesión y ve únicamente su portal de recompensas y referidos, mientras que el personal administrativo entra a los módulos clínicos y financieros según su rol.

Ventajas Clave (Puntos a Favor)

  • ✓ Sincronización en Tiempo Real instantánea: Cuando recepción marca "Asistió" a un referido en la pantalla admin, el paciente ve de inmediato su recompensa liberada en su portal. No hay APIs intermedias ni retrasos.
  • ✓ Un Solo Dominio y Hosting en Vercel: Despliegas una sola vez (ej. holistica.com o app.holistica.com). 0 complicaciones de DNS, SSL o cookies cross-domain.
  • ✓ Componentes y Estilos Compartidos: La identidad visual (colores de Holística, tipografías, botones, modales, iconos) se diseña una sola vez y se reutiliza.
  • ✓ Next.js App Router separa el código solo: Gracias al Route Grouping /(pacientes) y /(admin), Next.js empaqueta el JS de forma aislada. Los pacientes no descargan el código de finanzas.
  • ✓ Mantenimiento 10x más ágil: Solo tienes un repositorio en GitHub, una sola lista de dependencias y una sola base de configuración.

Puntos en Contra / Cuidados a tener

  • ⚠️ Requiere RLS estricto en Supabase: Si alguien escribe una consulta sin RLS, podría haber fuga de información. Debe configurarse que un paciente solo pueda consultar sus propios datos.
  • ⚠️ Middleware de autenticación mandatorio: Las rutas /admin/* deben estar protegidas a nivel servidor para expulsar de inmediato a cualquier usuario no autorizado.
Complejidad de Mantenimiento: Baja Costos de Infraestructura: Mínimo (1 solo proyecto)

Opción 2: Dos Apps Separadas

Frontend Pacientes + Frontend Admin en repositorios distintos

Crear dos aplicaciones web distintas: una pública (pacientes.holistica.com) para consulta de puntos/referidos, y otra privada (admin.holistica.com) para la gestión médica interna.

Ventajas (Puntos a Favor)

  • ✓ Aislamiento total de código: Es físicamente imposible que un paciente vea una pantalla admin filtrada en el bundle de JS, porque ese código simplemente no existe en su repositorio.
  • ✓ Aislamiento de tráfico masivo: Si lanzas una campaña en redes sociales y entran 5,000 pacientes simultáneos, el portal de pacientes absorberá la carga sin afectar la fluidez del sistema admin de la clínica.

Puntos en Contra (Desventajas Severas)

  • ✕ Doble trabajo y doble mantenimiento: Cada cambio visual, actualización de paquetes o ajuste en el diseño debe replicarse manualmente en dos proyectos diferentes.
  • ✕ Doble despliegue en Vercel: Tienes que gestionar 2 proyectos en Vercel, configurar variables de entorno duplicadas y vigilar límites de planes gratuitos/pro por separado.
  • ✕ Autenticación y Sesiones Cruzadas Complejas: Si quieres compartir sesión o cookies entre dominios diferentes, Supabase requiere configuración avanzada de cookies seguras y dominios autorizados.
  • ✕ Igual necesitas RLS en Supabase: Aunque tengas 2 apps, ambas atacarán la misma base de datos Supabase. Por ende, la seguridad de datos se tiene que hacer en Supabase de todos modos. Separar el frontend no te ahorra la seguridad de backend.
Complejidad de Mantenimiento: Alta (Doble repo) Costos de Infraestructura: Mayor (2 proyectos Vercel)

¿Cómo se garantiza que un Paciente NUNCA vea datos Admin?

El "Tridente de Seguridad" estándar de la industria

1 Middleware de Next.js

Filtro de Rutas en Servidor

Si un paciente intenta teclear directamente en su navegador /admin o /admin/rentabilidad, el archivo middleware.ts intercepta la solicitud antes de renderizar y lo redirige automáticamente a /portal-pacientes o al login.

2 Supabase RLS (Row Level Security)

Blindaje en Base de Datos

Incluso si un paciente con conocimientos de informática lograra ejecutar una petición fetch a la API de Supabase pidiendo los "ingresos" o los "costos", la base de datos de Supabase evalúa su rol y responde con 403 Acceso Denegado.

3 Route Groups Aislados

Code Splitting de Next.js

En la carpeta src/app/ separamos:
📁 (admin)/admin/...
📁 (paciente)/portal/...
El navegador del paciente jamás descarga el código JavaScript de los gráficos ni de los reportes del admin.

│   │

│   │   ├── admin/
│   │   │   ├── page.tsx          # Dashboard de métricas generales
│   │   │   ├── referidos/page.tsx# Gestión y aprobación de referidos (Imagen 2)

│   │   │   └── seguimientos/     # Seguimientos clínicos
│   │
│   └── middleware.ts             # Guardián de seguridad: Si no es admin, bloquea /(admin)
